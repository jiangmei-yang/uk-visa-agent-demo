# Gmail 使用方式：直接咨询

`service_request` 模式直接处理客户主动发来的咨询和材料，不要求先复制同意句子、
回复参考码，也不发送独立的授权邮件。业务邮件不自动附加资料处理或模型供应商说明，
正文只保留当前咨询内容和下一步。不得因此宣称回复来自真人。
客户可以要求停止处理。材料确认、客户档案隔离、人工审核和最终发送检查不变。

这是运营者选择的服务交互模式，不是客户同意的证据，也不是法律合规结论。
真实部署前，运营者仍须确定适用的资料处理依据、告知方式和供应商安排。
当前服务会在本地保存客户提供的资料，并将相关文字交给配置的模型供应商辅助整理和回复。
部署者应在适当的客户可访问入口提供隐私信息；移除邮件页脚不等于免除这些责任。
程序不会伪造同意记录，停止处理也不会自动删除已有资料或撤回供应商已收到的内容。

使用现有 Gmail 配置，按服务邮箱接收任意发件人的普通咨询，不要求指定主题：

```sh
.venv/bin/python scripts/gmail_sandbox.py serve \
  --accept-new-senders --mailbox service@example.com \
  --after ACTIVATION_UNIX_TIMESTAMP --state-dir data/new-service \
  --processing-interaction service_request --watch --interval 30
```

替换服务邮箱和启用时间；同一个服务邮箱只运行一个收件进程。
`--sender customer@example.com` 仍可用于有意限定的开发测试，但不再是普通客户入口。
每个 Gmail 线程独立建档并绑定原发件人；不会仅因邮箱相同自动合并不同申请。
自动回复、退信、邮件列表、垃圾箱、草稿、自发邮件及其他客户插入的线程消息会被过滤。

切换旧单发件人部署时，先停掉所有重叠进程，保留原状态目录，设置新的启用时间，
并增加 `--migrate-service-interaction`。迁移保留客户档案、原绑定备份与旧同步记录，
建立新的全发件人同步记录和明确的切换时间；只有切换之后的新邮件进入新流程。
既有拒绝或停止状态继续有效。不会回扫旧暂存内容，也不会补造客户同意记录。
默认 `explicit_consent` 为旧部署保留原有行为；新模式必须在启动时明确选择。

## 指定案件发送和核查

开放收件不等于开放批量发送。人工检查完待发送内容后，必须同时指定案件和客户邮箱：

```sh
.venv/bin/python scripts/gmail_sandbox.py send-reviewed \
  --case CASE_ID --sender customer@example.com --mailbox service@example.com \
  --state-dir data/new-service --processing-interaction service_request
```

`CASE_ID` 必须是该档案库中属于该客户的 Gmail 案件。命令每次最多处理该案的一条待发消息，
不会领取、失败标记或发送其他案件的队列项，也不会修改开放收件绑定或资料处理配置。
这不是审核批准命令：最终材料仍须已有当前客户确认、有效材料包和全部发送前检查。
没有材料包或确认失效时，命令不会绕过门禁。

发送结果不明确时，把上述命令的 `send-reviewed` 换成 `reconcile`，核查该案件已经尝试的发送。
核查不重发邮件；没有找到明确的供应商记录也不能当成发送成功或直接再次发送。
现有带限定主题的部署仍需提供原来的 `--subject`，不得借案件选择修改收件范围。
如果收件进程正持有状态锁，等待该轮完成后再执行，不要另开一个发送进程抢占。
