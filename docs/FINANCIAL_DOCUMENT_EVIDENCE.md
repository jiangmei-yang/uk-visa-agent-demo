# 普通财务材料的来源绑定与一致性检查

2026-09-05。本轮补的是此前验收审计明确列出的结构缺口：普通 PDF 虽然能被识别为
工资证明、银行账单或资助人资金证明，却没有可比较的金额、币种、日期、周期及
持有人证据。只按文件类别放行会把“看见一份银行账单”误当成“这份资金属于正确的
人且内部一致”。

## 当前实现边界

每条财务观察分别保存持有人、金额、日期以及可选账户引用的页码和连续原文。
金额保持原币，不换汇、不求和；余额不变成收入，文档值也不自动覆盖客户自己确认的
年收入、旅行预算、资金方式或资助人。工资只在姓名、币种、月／年周期、gross／net
口径和材料日期相同的来源间比较；余额还要求相同的非空账户引用。不同币种、日期、
账户、持有人或口径不构成自动冲突。

申请人银行账单和工资证明的持有人会与档案姓名核对，资助人资金证明会与已知资助人
姓名核对。差异只标记为需要解释的一致性问题，不判断欺诈。问题正文不回显姓名、金额
或完整账户引用。来源失效、被替换或比较口径变化后，旧问题会以“不再存在当前可比
来源”解决，不会永久卡住材料包。

普通 reader 产生的工资证明、银行账单或资助人资金证明，如果缺少可重新验证的结构化
观察，会被人工复核或不能满足交付要求。只有明确的 marker-driven 合成演示保留兼容；
它在证据报告中始终标为 `DEMO_SYNTHETIC`，不计作普通材料验证。资金要求同时按客户
当前分支选择本人银行账单、学校／雇主资助信或个人资助人资金证明；在读证明不能满足
在职分支，反之亦然。

## 失败记录和修复依据

四份虚构、无提取 marker 的 A4 PDF 已渲染为 PNG 并逐页查看，文字完整、无裁切、重叠
或黑块。它们明确写明非真人、非真实账户或雇主。

- v1 实际调用四次 DeepSeek：1 通过、3 失败，共 7,689 tokens。系统安全地把失败材料
  置为人工复核，但当时没有保存文档模型原始 JSON，无法定位失败层。
- 增加显式诊断捕获后，v2 只重测三项失败：0 通过、3 失败，共 5,823 tokens。原始 JSON
  显示姓名、金额和币种均正确；后置校验错误地要求日期和账户引用也出现在金额同一句。
- 将持有人、金额、日期、账户引用拆成独立来源定位后，v3 的三项均通过，共 6,414 tokens。
- 旧版通过的资助人样本不能证明新结构，v4 因此仅重测该项一次并通过，共 2,108 tokens。

合计 11 次、输入 18,612、输出 3,422，共 **22,034 tokens**；无重试、无 Gmail 调用，
实际费用以 DeepSeek 账单为准。v1/v2 失败未删除或覆盖。v3+v4 的四个当前提案可以在
禁止网络的测试中重新验证，并会从两份同账户、同日期、同币种、不同金额的账单生成
一个脱敏 blocker。

v2 原报告的 `scope` 误写为四份 PDF；其 `maximum_model_calls` 和保留结果均明确是
三份（0 通过、3 失败）。为保留原始证据，v2 文件未被改写，勘误记在 rollout manifest。
该 manifest 同时冻结 v1–v4 报告文件的 SHA-256，离线重放会先核对报告和 PDF 字节。
同时，v1–v4 在新证据契约之前产生，没有保存源文件组合、schema、实际 prompt、请求配置、
Git 修订、run ID 和 provider 返回模型绑定；现在的离线哈希核对不能追溯性地补齐这些
历史字段。后续 probe 必须在创建 provider client 前同时匹配冻结 PDF SHA-256 和明确的
`FICTIONAL SPECIMEN FOR SOFTWARE EVALUATION` 标记，并在新报告中保存上述哈希与运行元数据。
